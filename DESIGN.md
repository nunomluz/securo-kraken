# Design notes

Why the plugin works the way it does. Decisions are numbered D1 onwards. The full design, with the sources behind the ledger rules, is in `docs/superpowers/specs/2026-11-22-kraken-plugin-design.md`.

The plugin is a provider plugin: `sync` returns the account's records (contract 1) and Securo writes them through the same pipeline its native bank connections use, matching each record by `external_id`. Kraken's Spot REST API is the source: signed POSTs for the two private methods, plain GETs for public data.

## Decisions

| # | Decision | Why |
|---|---|---|
| D1 | Read-only, and only two key permissions: Query Funds and Query Ledger Entries. Private calls are only `BalanceEx` and `Ledgers`; public calls only `Assets`, `AssetPairs`, `Ticker`, `Trades`. The manifest declares no `api_scopes`. | The plugin returns records and writes nothing itself. A key that can't trade or withdraw limits the damage of a leak. |
| D2 | Public plugin. No keys, secrets, balances, coins held, ledger ids or real amounts in the repo; every fixture is made up. Error messages and logs are fixed text or sanitised type names, never credentials, signatures, URLs with queries, response bodies, amounts, ids, coins or dates. | Anyone can read the code, and logs end up in the plugin-runner log. |
| D3 | Standard-library Python only, no lockfile. External-id formats are frozen: account `kraken:<CCY>`, cash `kraken:<ledger id>` and `:fee`, holding `kraken:<COIN>`, trades `kraken:<ledger id>`, `kraken:reward:<COIN>:<YYYY-MM>`, `kraken:opening:<COIN>`, `kraken:adjust:<COIN>`. | Securo matches every record by its external id, so a format that changed would duplicate what is already synced. Securo prefixes holding ids per connection, so nothing per-connection is needed. |
| D4 | Ledger through the live API (approach A), not the CSV export or `TradesHistory`. | One endpoint and one permission give trades, deposits, withdrawals, Earn moves, rewards and fees. The CSV export creates reports in the person's account (a write), needs another permission and has undocumented columns; `TradesHistory` adds a permission for a second copy of the same facts. |
| D5 | One Securo connection per Kraken API key. A sub-account has its own keys, so it is another connection. | Keeps accounts and holdings scoped the way Securo scopes them. |
| D6 | Swaps carry the cost over: the coin given up leaves at its average cost (no gain) and the coin received takes it. | Needs no historical price per swap. The person chose it over selling at market. |
| D7 | Earn rewards are bought at zero cost (they show as gain); withdrawals leave at average cost (no gain); airdrops and forks (`transfer` with no subtype) cost zero; crypto deposits, including from the Futures wallet, are bought at the market price at the time. | The person's choice for rewards and withdrawals; deposits have no cost information, so market is the honest default. |
| D8 | Fiat becomes cash accounts (type `investment`, `kraken:<CCY>`); everything else, stablecoins included, becomes one holding per coin family, spot and Earn combined, with the split in metadata. Fiat in Earn stays in the fiat account. All coins sit in one "Kraken" wallet. | Securo requires a three-letter currency on accounts, so USDT and USDC can't be accounts. One asset per coin avoids counting Earn twice. |
| D9 | Asset codes are reduced to a family: strip `.S .M .P .F .B` (then trailing digits, except `ETH2`), strip `.HOLD`, map through `Assets` altnames, then fixed aliases (`XBT` to `BTC`, `XDG` to `DOGE`, `SETH` and `ETH2` to `ETH`, `FLOWH` to `FLOW`). `KFEE` is ignored. | Every flavour of a coin must land in one holding or the quantity would not add up. |
| D10 | One valuation currency per connection (default EUR), fixed at the first sync; a change is `NeedsAuth` asking for a new connection. | Cost basis and trade prices are in that currency; switching mid-life would make the stored ledger inconsistent. |
| D11 | Rewards of one coin in one UTC month are sent as one trade, `kraken:reward:<COIN>:<YYYY-MM>`, resent with its growing quantity during the month. | Daily or hourly dust would round to 0 at Securo's six decimals and could exceed the trade cap. |
| D12 | Buys and sells are not cash transactions; deposits, withdrawals, fees, fiat rewards and fiat-to-fiat conversions are. | Trades belong to holdings, as in the Trading 212 plugin. |
| D13 | Classification follows Kraken's support article, rotki and ccxt, applied in a fixed order (internal, rewards, trades by refid, deposits and withdrawals, anything else by sign). Unknown types and subtypes are classified by sign and logged by name only. | There was no Kraken key during development. The balancing trades (D17) mean a misread row can misprice a lot but never misstate a balance. |
| D14 | Time budget 40 s of Securo's 60 s; the ledger walk stops at 30 s so prices still fit. Private calls are paced against an estimated counter (max 15, decay 0.33/s, `Ledgers` costs 2); public calls at most one per second. Running out of time or a rate-limit reply stops the work, keeps the position and returns what was gathered; it is not a failure. | Roughly 700 ledger entries fit in one sync on a starter account, so long histories take several hourly syncs. Kraken sends no rate-limit headers. |
| D15 | The ledger is walked newest to oldest by `end` timestamp, never with `ofs`, de-duplicated by remembered ledger ids. When a resumed full page brings nothing new and its rows all sit at the cursor time, the cursor steps down 0.0001 s and a warning is logged; backfill is never marked complete from a stalled page. Incremental reads re-read an overlap of one hour and stop only when a page reaches below the floor or has fewer than 50 rows. | A silent "complete" would release holdings with a hole in the history. Kraken times have four decimals, so 50 rows at one instant is near impossible; if it happens the tied rows are skipped and the balancing trades cover the quantity. The overlap exists to catch late rows, so "nothing unseen" must not stop it. |
| D16 | Holdings and trades are sent only once the backfill is complete and every price they need is known; until then `holdings` is left out (`null`, never `[]`). Cash transactions go out as they are collected. Holdings also wait while rows are held back (D18), which is bounded to about an hour. | Before that the trades can't add up. `null` means "not fetched" to Securo, whereas `[]` would archive everything. |
| D17 | When the trades don't add up to the reported quantity, an opening buy (dated before the first known event, at the market price on its date, dated at UTC midnight) and an adjustment sell (dated the sync day, at average cost) are sized from scratch every sync and resent under the same ids; one no longer needed is resent at 0.000001. Neither may create a gain when made. | Securo keeps a coin's trades only if a by-date replay never dips below zero and ends on the reported quantity, and a stored trade can only be overwritten, never deleted. |
| D18 | A refid whose legs may not all be in yet is held back while it sits at the newest edge of what was read; older lone legs are final. The edge is taken from the wall clock when the walk has caught up (`max(newest, now)` minus the one-hour overlap), and rows held at the stop time of an interrupted walk are held too. | Otherwise a final lone leg would wait forever, and a swap's second leg on the next page would be booked as two separate lone trades. |
| D19 | Trades are priced by replaying them in Securo's own order: by date, buys before sells, then external id, settling each day's average-cost sells on the values Securo stores (quantity and price rounded half-up to six decimals, fees to cents), with a day's coupled averages solved exactly rather than iterated with a cap. Trade quantity and price are rounded to six decimals before they are sent and before any replay. Members of a swap are all dated by the group's earliest time. | An average-cost sell must go at the average Securo itself will compute, or Securo realizes made-up gains from rounding. Carried cost must be conserved across a swap. |
| D20 | Trade fees are rounded half-up to two decimals. | Securo's fee column has two decimals; full-precision fees make average-cost sells realize sub-cent gains there. |
| D21 | Prices are best effort. Current prices come from one `Ticker` call per sync, by direct pair, else via USD, else via BTC; historical prices from public `Trades` at the event time, cached by pair and UTC hour, with the next available price as fallback. A failing price call is caught and logged with fixed text, and the sync carries on with what it has; a coin with no price keeps its last value, else 0. A coin that can't be priced historically gets a historical price of 0, logged. Tokenized-asset legs go in their own `Ticker` call and never overwrite plain results. | A price outage must not throw away a sync's ledger and cash progress. The cost is that a persistent outage silently delays holdings (a warning is logged). |
| D22 | A coin is sent value-only (`trades: null`, quantity kept, cost in `purchase_price` from the plugin's own exact running cost) when any average-cost, market or fixed trade price, or the current price, is below 0.01 in the valuation currency, and once so it stays so (state). Trades priced exactly 0 from rewards don't count. A coin whose quantity is 1e9 or more is sent with `quantity` and `trades` null as well. | Securo stores trade prices to six decimals and replays cost as quantity times stored price, so a micro-priced coin would get several-percent cost errors and made-up gains. Counting zero-cost rewards would make any coin with swapped rewards permanently value-only. A quantity over nine digits doesn't fit Securo's column. |
| D23 | Coins sold out stay holdings with quantity 0, kept in state and listed on every sync. Every coin ever seen is listed every sync. | Securo archives a holding its provider stops listing, which would take a sold position off the Assets page. |
| D24 | Dust below 0.000001 is lost, and a trade whose quantity rounds to 0 is not sent (the balancing trades cover the units). | Securo stores six decimals and requires trade quantity above zero. |
| D25 | Rewards of fiat (`staking`, `reward`, `earn` reward) read "Kraken rewards"; dividends, invite bonuses and airdrop transfers on fiat are described by their type. Futures, margin and NFT movements are recorded by net effect: outflows at average cost, inflows at market, logged by type name only when unknown. | Keeps the fiat account's activity explaining its balance without pretending those products exist in Securo. |
| D26 | Errors: an invalid key or signature, an empty key or secret, an unknown currency, a currency change, a permission-denied reply (naming which permission) or an OTP-protected key is `NeedsAuth` with a fixed message. An invalid nonce is retryable, with a message suggesting a key used only by Securo. `EAPI:Bad request`, 5xx, lockouts and network errors are retryable. | Securo stops all scheduled syncs on `NeedsAuth`, so it is reserved for problems only the person can fix. A bad request is not a credential problem. |
| D27 | The nonce is `max(int(wall_ms), last + 1)`, and the key and secret are checked for a safe character set before they are used. | Kraken needs a strictly increasing nonce per key, and a malformed credential must never reach a message. |
| D28 | The account names its logo by key (`institution_logo: "kraken"`) and the file ships in the package. The mark is original artwork, not Kraken's. | Securo refuses a logo URL on an undeclared host, and the plugin has no right to the service's trademarks beyond naming it. |
| D29 | Amounts are plain decimal strings with at most 8 decimals, never floats. Replies are capped at 20,000 trades and 20,000 transactions. | The contract refuses floats and longer fractions, and caps replies. |
| D30 | Released as 0.1.0 and marked beta; the README points to `tools/kraken_probe.py`, which prints only the shape of a ledger, for safe reports. | No Kraken key was available during development, so the first real sync is the real-data check. |
